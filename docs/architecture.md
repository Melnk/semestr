# Архитектура

## Границы

Модульный монолит Kotlin/Spring Boot. Транспортные DTO и REST-контроллеры вызывают сервисы; сервисы проверяют правила и ведут транзакции; `StudyRepository` работает с PostgreSQL. Никакая бизнес-логика не зависит от React или Tauri.

- `accounts`: профиль, пароли, email-проверка/восстановление, сессии, rate limits и HTTP-фильтр.
- `study`: предметы, задания, долги, заметки/ссылки; пять отдельных типов доменных данных, общая проверка принадлежности и механизм версий.
- `schedule`: локальные повторения, преобразование в моменты времени, исключения и пересечения.
- `transfer`: целостный экспорт, валидация, предпросмотр, импорт с заменой или добавлением.
- `common`: единые ошибки и OpenAPI.

Предметы/задания/долги/заметки пока используют один модуль `study`: они имеют общие правила ссылочной целостности. Их можно разделить на пакеты при росте отдельных сервисов, не превращая приложение в микросервисы.

## Данные

`accounts` хранит профиль, email, BCrypt-хеш и общую ревизию пространства. `study_records` хранит типизированный JSONB payload, вид сущности, владельца, версию и явные колонки связей. Это не произвольное JSON-хранилище: Jackson принимает закрытый набор DTO, неизвестные поля и типы отклоняются; сервис проверяет значения и ограничения длины.

Колонки `subject_id`, `debt_id`, `lesson_id` имеют составные внешние ключи `(user_id, id)`. Они не дают записать ссылку на чужие данные даже при ошибке вызывающего кода. Сервис дополнительно проверяет тип объекта и совпадение предмета. Прямой доступ прикладных пользователей к PostgreSQL не предоставляется. RLS не используется; границей авторизации служит API плюс составные FK.

AcademicDebt — отдельная запись с собственной историей закрытия, ссылающаяся на предмет. Задания не закрывают долги/предметы автоматически. Для закрытия долга нужны дата и подтверждение. Состояния можно исправлять в обе стороны: это личный планировщик, а не официальная ведомость. «Принято» не является цифровой подписью преподавателя.

Все изменения учебных записей блокируют строку владельца до конца транзакции и увеличивают общую ревизию. `UPDATE ... WHERE user_id=? AND id=? AND version=?` защищает от потерянных изменений. Импорт проверяет общую ревизию предпросмотра, блокирует владельца и выполняет все записи в одной транзакции. Прямое удаление предмета с зависимыми записями запрещено; удаление аккаунта каскадное. При добавлении/замене импорта идентификаторы переназначаются, включая связи и исключения.

## Время

Дедлайн задания — `Instant`, срок долга — `LocalDate`. Серия занятия — `LocalTime` + `ZoneId` + период `LocalDate`. Java TZDB учитывает DST. Если конец раньше начала, он относится к следующему локальному дню. Для весеннего разрыва используется стандартная политика Java — сдвиг вперёд на разрыв; для осеннего двусмысленного времени — более ранний offset. Эта политика покрыта тестами и должна оставаться стабильной.

Неделя № 1 задаётся понедельником. Чётность вычисляется относительно этого дня, а не ISO-номера недели в году. Отмена хранит исходную локальную дату и пустые новые моменты; перенос — исходную дату и два `Instant`. Исключения могут попасть в другой месяц и часовой пояс. Поиск включает перенесённые события независимо от исходного диапазона. Изменение серии запрещено, если существующее исключение перестало бы соответствовать серии.

## Клиенты

Веб: `apps/web`. Общий API-клиент: `packages/api-client`, DTO генерируются из OpenAPI. Tauri использует ту же опубликованную веб-версию, поэтому отдельного UI-пакета с копиями компонентов нет. `packages/ui` намеренно не создан: код интерфейса физически один и пока не импортируется двумя отдельными сборками.

Будущий iPhone-клиент сможет использовать REST v1 и bearer-аутентификацию. Для нативного клиента токен хранится в Keychain, не в UserDefaults и не в browser localStorage. В текущем браузере и Tauri используется HttpOnly cookie, доступная только сетевому стеку WebView. JS хранит CSRF-токен только в памяти.

## Соединение и несколько серверов

Сервер — источник истины. Черновики учебных форм хранятся локально с ID аккаунта и исходной версией. Они не отображаются как сохранённые серверные записи. Пароли, сессионные токены и содержимое форм входа в localStorage не сохраняются. Выход/удаление аккаунта очищают его черновики на данном устройстве; другие устройства очищаются при следующем входе/выходе вручную, локальный диск вне серверного контроля.

Сессии, одноразовые токены и ограничения частоты хранятся в PostgreSQL, не в памяти процесса. Sticky sessions не нужны. Все серверы используют одну БД, SMTP, одинаковые Origin/cookie-настройки и актуальную TZDB. Каждый экземпляр выполняет Flyway с блокировкой миграции. Нет очередей или обязательного Redis. Для production полезно добавить отдельную фоновую очистку истёкших rate_limits/email_tokens; очистка сессий уже выполняется при входе.
