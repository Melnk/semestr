# Самостоятельное размещение

## Один сервер

Нужны Linux с Docker/Compose, домен, HTTPS reverse proxy и SMTP. На сервере скопируйте `.env.example` в локальный `.env`, заполните секреты и не коммитьте файл.

Обязательные параметры: случайный `DATABASE_PASSWORD`, `APP_ORIGIN=https://ваш-домен`, `SECURE_COOKIE=true`, `SMTP_HOST/PORT/USER/PASSWORD`, `SMTP_AUTH=true`, `SMTP_TLS=true`, `MAIL_FROM` на подтверждённом домене. Настройте SPF/DKIM/DMARC у почтового провайдера. Укажите `SMTP_PORT=587`, если провайдер требует STARTTLS; для implicit TLS 465 дополнительно задайте `SPRING_MAIL_PROPERTIES_MAIL_SMTP_SSL_ENABLE=true` и отключите STARTTLS.

В `infra/compose.yml` задайте backend реальные SMTP-параметры вместо `mail:1025`. Удалите зависимость backend от `mail` и не запускайте Mailpit на публичном сервере. Удалите публикацию порта БД — PostgreSQL должен быть доступен только в Docker network. Запускайте backend/web/db. Локальный compose — пример для разработки; его SMTP-настройки специально не отправляют реальную почту.

```sh
docker compose --env-file .env -f infra/compose.yml --profile full up -d --build
```

`web` слушает только `127.0.0.1:8088`. Установите Caddy/Nginx с HTTPS перед ним; пример — `infra/Caddyfile.example`. Приложение/API имеют один origin. Не включайте широкую CORS-политику. Проверяйте отсутствие открытых 5432/54329/1025/8025 на публичном интерфейсе.

Health check: `GET /actuator/health`. Ответ не раскрывает подробности БД. Nginx ограничивает body 5 МБ и добавляет CSP, nosniff, frame denial и no-referrer. Включите HSTS на HTTPS reverse proxy после проверки сертификата. Не логируйте request body, cookies, Authorization и email-токены. Spring пишет структурированные JSON-логи; подключите свою ротацию и сбор логов.

## Несколько экземпляров

Сессии и rate limits хранятся в PostgreSQL, sticky sessions не требуются. Масштабируйте backend за reverse proxy с одной БД и одинаковыми конфигурациями. Запускайте миграции перед переключением трафика. Учтите per-user блокировку на запись: один пользователь не должен одновременно делать огромные импорты на многих устройствах. Чтения обычных записей не блокируются.

IP-limit не доверяет произвольному X-Forwarded-For. За proxy все клиенты по умолчанию имеют его адрес, поэтому настройте дополнительный rate limiting на доверенном edge или явно сконфигурируйте Tomcat RemoteIpValve с allowlist вашего proxy. Не включайте доверие ко всем forwarding headers. Email-limit уже общий для всех экземпляров.

Очистка просроченных `email_tokens` и `rate_limits` может выполняться ежедневной операционной задачей БД: `DELETE ... WHERE expires_at < now()`. Не удаляйте ещё действующие сессии/токены. Политика хранения резервных копий учитывает персональные данные.

## Резервное копирование

Из каталога развёртывания, используя защищённый каталог вне Git:

```sh
mkdir -p backups
docker compose -f infra/compose.yml exec -T db pg_dump -U semestr -d semestr -Fc > backups/semestr.dump
```

Проверьте exit code и ненулевой размер. Шифруйте копию, ограничьте доступ, храните версию схемы и конфигурацию без секретов отдельно. Backup содержит профили и учебные данные, хеши паролей и действующие сессии; не публикуйте его. Для этого сценария JSON-экспорт не заменяет административный backup.

## Восстановление

Сначала восстановите в отдельную пустую БД и проверьте версию приложения, количество пользователей/записей, вход, чтение предмета и экспорт. Команды ниже относятся только к подготовленному окружению восстановления:

```sh
docker compose -f infra/compose.yml exec -T db createdb -U semestr semestr_restore
docker compose -f infra/compose.yml exec -T db pg_restore -U semestr -d semestr_restore --no-owner < backups/semestr.dump
```

Переключите проверочный backend на `jdbc:postgresql://db:5432/semestr_restore`. Для производственного переключения назначьте окно обслуживания и остановите записи. После восстановления разумно отозвать все сессии и email-токены в восстановленной БД, чтобы старые ссылки не стали действующими снова. Никакие разрушительные restore-команды автоматически приложением не запускаются.

## Обновления

Сделайте и проверьте backup, изучите миграции, соберите новую версию, выполните smoke-тесты на копии, переключите трафик. Flyway-миграции только вперёд; для отката схемы используйте проверенное восстановление. Внешний мониторинг и нагрузочное тестирование должен настроить владелец размещения.
